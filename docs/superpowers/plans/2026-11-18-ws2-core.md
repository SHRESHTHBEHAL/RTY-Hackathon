# Workspace 2: Core (Ledger and API) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Gaitway's ledger and HTTP API: accounts, agents and wallets, credentials, charges, settlement, and reconciliation against the vault.

**Architecture:** A Hono service over Postgres. All money movement goes through one double-entry ledger module that locks the affected rows in a single transaction. The vault is reached only through the `VaultClient` interface; an in-memory implementation stands in until the real one is plugged in. Background jobs credit deposits, release expired holds, settle sellers, and reconcile.

**Tech Stack:** Node 22, TypeScript 5, Hono, Drizzle ORM, Postgres 16, zod, jose, Vitest, Docker Compose for Postgres.

**Spec:** `docs/superpowers/specs/2026-11-18-agent-payment-gateway-design.md` and `context.md`. Read both in full first. `context.md` sections 6 to 10 are your contract.

## Review Focus

- Two credential requests arrive at once for a wallet that can afford only one: exactly one succeeds. (Task 6)
- A seller retries a charge after a timeout with the same idempotency key: one charge exists, and the reply is identical. (Task 7)
- A charge arrives in the same instant the credential expires and the sweeper runs: the money ends in exactly one place. (Task 7)
- The process dies after the vault settle call but before the database is updated: the next run finishes the batch without paying twice. (Task 9)
- A request body carries an amount that is negative, zero, fractional, has leading plus sign, or exceeds 2^63: it is rejected with `validation_failed`. (Task 1 helper, used everywhere)

## Ledger model (fixed by this plan)

Ledger accounts are rows identified by `(env, kind, ownerId)`:

| Kind | Owner | Meaning |
|---|---|---|
| `external` | `"vault"` | Money outside the ledger; the other side of deposits, payouts, withdrawals |
| `unallocated` | business ID | Business funds not in any wallet |
| `available` | wallet ID | Spendable wallet balance |
| `held` | wallet ID | On hold for open credentials |
| `owed` | seller ID | Charged, not yet settled, net of fee |
| `fees` | `"gaitway"` | Fees charged, not yet settled |
| `settling` | batch ID | In flight to the vault |

A **posting** is a set of entries that sums to zero. `post()` is the only
function that changes balances.

```ts
type Entry = { account: { kind: Kind; ownerId: string }; deltaMicros: bigint };
function post(tx: Tx, env: Env, type: string, ref: string, entries: Entry[]): Promise<string /* postingId */>;
function balanceOf(tx: Tx, env: Env, kind: Kind, ownerId: string): Promise<bigint>;
```

`post` locks the touched account rows in a fixed order (sorted by kind,
then owner) with `SELECT … FOR UPDATE`, rejects any posting that does not
sum to zero, and rejects any posting that would take a non-`external`
account below zero with `ApiError("insufficient_funds")`.

Each charge also records `businessId`, so settlement can group by business
and seller.
